## 1. 为什么要这份文件

主公裁决（原话）：「把我们的工作流写成一个文档。因为现在我们用的是国际版的 Agent，我一会儿想要切回国内版的 Qoder，直接把这个文件喂给他，他就能直接复用了。」

痛点是**工作流的生效面绑在产品能力上**：角色要靠注册表收编、Agent 清单在会话启动时快照、`.qoder/rules/` 靠 `trigger` 自动加载、`/feature-dev` 靠 slash 起编排。换一台产品（国内版 Qoder / Qoder IDE / 非 Qoder agent）这四项里任何一项不兼容，流水线就退化成"读得到的规矩、跑不动的流程"。

所以这份文档的定位不是重复 `docs/AGENTS.md` §9，而是把它投影成**不依赖产品专属能力的最小可执行集**：喂一个文件就能开工，能力缺失有明确降级路，且降级后仍守住做判分离。

## 2. 关键设计（三条）

1. **派发路 A/B/C 分级**：A 原生子智能体 → B 通用子代理先 `Read` 角色卡 → C 单会话串行扮演。B 的补偿两条（只读角色明令禁写 + 主会话 `git status --porcelain` diff 复核）是把 frontmatter 硬隔离失效后的口子用流程兜住；C 用「工序产物落盘 + 批卷必须重读文件并引用行号 + 显式角色切换分隔行」替代角色隔离，并**明写它是降级不是等价，全链需求须主公确认才走**。
2. **产品差异表**（§2.3）：把 rules 自动加载 / skills 落盘即用 / Agent 注册表 / 浏览器 MCP 四项各自列出"有则"与"无则"，避免新产品的 AI 因为某项缺失就整条流程停摆或悄悄跳验证。
3. **未知项不许凭猜**（§9）：Desktop 已实测的四条事实（skills 即时识别、放用户级目录即被注册表收编且无需 Settings 表单、Agent 清单会话启动快照、注册表条目会反向改写用户级镜像）单独成表，与"国内版四项未知"分开列，并给出实测顺序。这是为了防止下一个产品里的 AI 把国际版的行为当成通用真理。
