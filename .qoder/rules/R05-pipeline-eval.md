# R05 流水线与 Eval 质检约束

> 核心命题：把流转交给系统——每阶段 = 执行 Agent + 独立 Eval；做判分离，批卷的必须是另一个 AI。

## 1. 六道工序（执行角色 + 外挂 Eval）

| 工序 | 执行角色 | 外挂 Eval | 结构化产物 |
|---|---|---|---|
| 01 意图识别 | architect | ✅ Eval-01 | [REQ] 理解确认（验收标准可提取） |
| 02 编排规划 | feature-dev | —（编排自身即决策中枢） | biz 记录建档（[REQ]）+ 能力绑定清单 |
| 03 代码调研 | architect（可并行） | — | 调研结论并入 [PLAN] |
| 04 领域设计 | architect | ✅ Eval-04 | [DESIGN] |
| 05 编码实现 | coder（强制串行） | ✅ Eval-05 + reviewer 门禁 | 代码 diff + IMPL 清单 |
| 06 自动化验证 | test（做） | ✅ Eval-06 | 测试代码 + 执行结果 |

## 2. 门禁四态（编排读 Eval 结果决定，唯一决策点）

| 态 | 触发条件 | 动作 |
|---|---|---|
| 过 | Eval 三层全过 + reviewer 无 Critical | 进入下一道工序 |
| 警告 | Eval L2 建议项 / reviewer Suggestion | 记录理由后放行 |
| 回环 | 任一 Eval 层 fail / reviewer Critical | 打回对应执行角色重跑，仅传结构化失败清单 |
| 转人工 | 同一工序回环 2 轮仍不过 | 停止流水线，[VERIFY] 写"转人工"并附全部 Eval 结论 |

## 3. Eval 三层判定（eval-agent，判）

| 层 | 判定内容 | 依据 |
|---|---|---|
| G0 Shell Gate | 编译 / 执行 / 覆盖率 | 门禁命令（挂 scripts/check-*.sh）+ 构建命令（以 AGENTS.md 常用命令节为准）、测试实跑、覆盖分析 |
| L1 公共语义 | 断言有效性 / 边界异常 | 断言锚定业务意图而非代码路径 |
| L2 模块专属 | 按模块定制校验 | R01~R04 自检清单 + knowledge cards |

- 任一层 fail 即驳回重跑；eval 只输出结构化结论（层/过否/原因），不改产物、不参与编排决策
- 层级适用性：G0（编译/执行/覆盖）适用于 05/06 工序；01/04 工序以 L0 证据核验 + L1/L2 语义判定为主，无 G0 项不视为缺失

## 4. 做判分离与语义锚定（L1）

1. **做判分离**：test-agent（做）产出测试与执行结果；eval-agent（判）独立复跑判定；producer 不得自判质量
2. **业务语义锚定**：断言按 `Trigger → Action → Effect` 三元组编写，锚定业务意图
3. **断言来源四件套**：PRD（[REQ]）+ 前序探索（[DESIGN]）+ 代码 diff + 存量测试；缺来源的断言视为无效
4. **测得对 > 测得多**：覆盖率是 G0 参考指标，结果指标是断言对业务意图的锚定度

## 5. 泛化与沉淀机制（解决一类问题，L1）

1. **问题定性（工序 04 必做）**：[DESIGN] 开头必须声明定性：
   - **点问题**：一次性需求，记录定性理由后按常规设计
   - **类问题**：存在同类场景（如下次可能是另一种规则/另一种协议）→ 必须给泛化方案：类型编码/参数化/配置驱动/抽象公共层，并标注「泛化点」与扩展方式（先例：xrule 以 rule_type 支撑多规则类型，新类型零表改零码改）
2. **扩展成本声明**：类问题的 [DESIGN] 必须写明「新增同类需求的改动面」（理想：加枚举值/加配置，不改表不改核心代码）
3. **沉淀评估（收尾必做）**：编排判定本次方案/模式是否可复用，命中任一即沉淀：
   - 重复出现的编码动线 → 新 domain skill（走新增 skill 三登记）
   - 新发现的存量规律/先例 → 补 knowledge card 或对应 R 文件条款
   - 通用设计模式（如类型码扩展）→ 写入 [PLAN] 被否/采纳理由供后续引用
4. **不过度设计**：点问题禁止强行泛化；泛化成本超出当前需求收益时，记录取舍理由即可

## 6. 报告存档（技术方案分享，L1）

1. **触发**：需求发布（状态流转「已发布」）后，recorder 用 `base/archive-tech-report` 生成一份完整技术方案报告
2. **存放**：`records/reports/{YYYY-MM}/{YYYYMMDD}_{需求名}.md`（命名同 biz 记录，同需求同名）；biz=过程账本（机器友好），report=分享报告（人友好）
3. **读者与文风**：面向技术/产品/测试三类读者——先讲业务再讲技术，功能用业务语言+验收清单表达，技术细节可折叠到附录；正文叙述式可直读，**「源 [X]」出处标注一律收进文末附录，不进正文**；证据链不降级——数据/结论必须可回溯 biz 章节，只是不显式堆在正文里
4. **模板（九节，角色导读放最前）**：
   ```markdown
   # {需求名} · 技术方案报告
   > 一句话摘要（交付了什么 + 业务价值 + 当前状态）

   ## 快速导读（按需取阅）
   | 角色 | 先看 |
   |---|---|
   | 产品 | 业务背景与目标、功能交付清单 |
   | 测试 | 功能交付清单、质量与验证、上线事项 |
   | 技术 | 实现概览、复用与沉淀、附录 |

   ## 1. 业务背景与目标（为什么做）
   用户诉求与痛点、目标边界；需求演化时间线（如有多轮追加，用时间线叙述）

   ## 2. 功能交付清单（交付了什么）
   验收标准逐条表格：编号 | 功能（业务语言） | 交互形态 | 结果；每条对应业务场景而非代码行为

   ## 3. 实现概览（怎么做的）
   动线一图流（一行链路图）；改动规模；问题定性（点/类）与扩展方式（新同类需求的接入成本）；关键决策与被否方案（每个一句话原因）

   ## 4. 质量与验证（做得对不对）
   测试用例清单：按测试类分组逐条列出（用例名/场景说明/预期结果/是否通过），用例名必须与代码实际方法一致（先验证再列，禁止凭记忆编写）；组后附执行汇总（Tests run/Failures/Errors）；质检结论表（工序/结论/轮次）；遗留风险与验证环境要求（明确告诉测试哪些必须线上验证）

   ## 5. 上线事项（依赖什么）
   checklist：DDL/注册项/配置/前置依赖，每项带责任方与状态

   ## 6. 复用与沉淀（下次怎么更快）
   沉淀物及适用场景；新同类需求接入指引（如：加一个枚举值即可）

   ## 7. 经验教训
   回环/返工/环境坑，每条一句现象+一句教训（供后续需求避坑）

   ## 附录
   - A. 证据与出处：本报告各节对应 biz 记录章节；关键代码定位/命令输出摘录（原样搬运）
   - B. Eval 与门禁明细：四道工序结构化结论
   ```
5. **样式规范（看着舒服）**：
   - 标题层级最多三级（# / ## / ###），正文段落短（≤3 行），不堆叠加粗（一段至多一处强调）
   - 列表能用表格就用表格；表格列数 ≤5，内容超长换短句
   - 分隔线只用于大章节之间；符号只保留 ✅ / ❌ / — 三种，不用 emoji 堆砌
   - 首屏（摘要+导读）控制在十行内；全文结构：一句话懂 → 按需导读 → 分层展开 → 附录兜底

## 7. 反幻觉机制（证据链，L1）

1. **事实断言必须有证据**：产物中每条事实断言（接口/类/方法/字段/配置/行为描述/执行结果）必须带三类证据之一，否则按幻觉驳回：
   - **代码定位**：`文件路径#符号`（引用前必须已 Read/Grep 验证存在）
   - **命令实跑**：命令 + 原始输出（编译/测试/门禁结论不得转述）
   - **记录引用**：`records/{biz,sys}/` 或 knowledge card 原文引用
2. **禁止清单**：凭记忆描述存量代码、"应该/一般来说/通常" 表述当作事实、未验证即引用类名/路径/配置项、转述执行结果而不附输出
3. **eval 判定前置 L0 证据核验**：eval-agent 在 G0 之前逐条核验证据（抽查验证路径/符号真实性），发现虚构即整批驳回，记「证据缺失」
4. **转述即背书**：编排/门禁引用执行角色结论时，证据随结论一起传递，不得只传结论不传证据

## 8. 记录要求

- 每道带 Eval 工序的结论写入 biz 记录 [VERIFY] 章节（工序号 + 三层结论 + 轮次）
- 转人工必须在记录中留痕，附全部 Eval 结构化结论

## 自检清单

- [ ] 01/04/05/06 四道工序均有独立 Eval 结论
- [ ] 回环未超 2 轮；超轮已转人工留痕
- [ ] 断言含 Trigger→Action→Effect 锚定，非代码路径断言
- [ ] 产物中每条事实断言带代码定位/命令输出/记录引用证据，无"应该/一般来说"式表述
- [ ] [DESIGN] 含问题定性（点/类）；类问题有泛化方案与扩展成本声明
- [ ] 收尾完成沉淀评估；已发布需求有对应 reports/ 报告存档
